FE QUEST v97 — 長期保存・バージョン移行・MASTER復帰 横断監査

目的
v96で通常学習 → 総仕上げ → 7日前からのテーパリング → 前日 → 当日までの学習設計がつながった。

v97では、数か月使い続けるPWAとして次の3点を横断監査した。

1. 学習データが壊れたとき、本当に一つ前へ戻せるか
2. v96 → v97 → 将来版と更新しても、学習履歴を壊さないか
3. 一度MASTERになったテーマが時間経過で崩れたとき、最初からやり直さず復帰できるか

今回も実ブラウザE2Eではなく、Node構文検査・抽出した永続化ロジックの実行テスト・静的契約検査を中心に確認した。

────────────────────
1. v96で見つかった実運用上の弱点
────────────────────

A. LAST_GOODが「一つ前」ではなかった
v96ではsaveProfile()のたびに、

現在データ
fequest_profile_v4

と

自動保護
fequest_profile_last_good_v1

へ同じJSONを書いていた。

したがって、外部要因で現在データだけが壊れた場合には役立つが、
アプリ自身が誤った状態を正常保存した場合、LAST_GOODまで同じ状態へ更新される。

v97では保存順序を変更した。

旧:
現在 ← 新データ
LAST_GOOD ← 新データ

新:
LAST_GOOD ← 保存前の正常な現在データ
現在 ← 新データ

これによりLAST_GOODを本当の「一世代ロールバック」にした。

TWO_GENERATION_LOCAL_ROLLBACK_OK

────────────────────
2. 現在データにも整合性チェックを追加
────────────────────

v96では書き出しJSONにはFNV-1aのchecksumがあったが、
ブラウザ内の通常保存データそのものにはchecksumがなかった。

v97では

fequest_profile_checksum_v1
fequest_profile_last_good_checksum_v1

を追加。

起動時に現在データのchecksumが一致しなければ、
現在データをそのまま正常扱いせず、LAST_GOODから復旧する。

テストでは、
正常保存 XP=2 のJSONだけを手動で XP=999 に変更し、checksumを古いまま残した状態を作成。

結果:
checksum mismatchを検出
→ LAST_GOODのXP=1へ復旧

PRIMARY_CHECKSUM_RECOVERY_OK

────────────────────
3. 長期復旧点をIndexedDBへ最大4件保存
────────────────────

localStorageは現在データ＋一世代ロールバックに使う。
さらにv97ではIndexedDBへ長期復旧点を追加した。

保存先:
fequest_recovery_v1
profileSnapshots

保持:
最大4件

通常保存:
30分に1回まで

強制保存:
バックアップ読込前
バックアップ読込後
読込前状態への復元時

目的は、
「現在」と「一つ前」が両方使えない場合にも、
少し古い正常状態へ戻れるようにすること。

起動時:
現在データ異常
→ LAST_GOOD異常/なし
→ すぐ新規データで上書きしない
→ IndexedDBの新しい復旧点から順に整合性確認
→ 有効なものがあれば自動復旧

有効な復旧点が1件もない場合だけ、
破損元をfequest_profile_corrupt_recoveryへ退避した上で新規状態を保存する。

LONG_TERM_INDEXEDDB_RECOVERY_ENGINE_OK

注:
IndexedDBの実ブラウザI/Oは今回E2Eしていない。
API契約・構文・復旧順序を監査した段階。

────────────────────
6. v96で書き出したバックアップも読める
────────────────────

重要な互換性問題があった。

v96のfequest-backup-v2は、
schema v3へ正規化したデータに対してchecksumを計算している。

v97で単純にschema v4へ正規化してからchecksumを計算すると、
正しいv96バックアップまで
「整合性チェック失敗」になる。

そこでv97には
normalizeProfileDataV3ForChecksum()
profileIntegrityChecksumV3()

を追加。

schema 3のfequest-backup-v2だけは、
v96と同じ正規化ルールでchecksumを検証してからv4へ移行する。

実際のv96コードから抽出したchecksumと、
v97互換関数のchecksumを同一サンプルで比較。

v96       fnv1a32:7b386ddd
v97 legacy fnv1a32:7b386ddd

完全一致。

V96_CHECKSUM_COMPAT_EXACT_OK

────────────────────
7. 将来版データを古いアプリで壊さない
────────────────────

v96の通常loadProfile()は、
localStorageのprofileSchemaVersionが現在より大きくても、
normalizeProfileData()で現在schemaへ変換して保存する余地があった。

例えば将来v110で新しい学習証拠を追加した後、
古いPWAキャッシュが起動すると、未知データを意図せず書き換える危険がある。

v97では

保存データ schema > 4

を検出すると、

FUTURE_PROFILE_SCHEMA

として起動。

その間:
- 現在rawを変更しない
- saveProfile()を停止
- 自動保存も停止
- 「FE QUESTの更新が必要」と表示

する。

Nodeテスト:
schema 5 / XP 999を投入
→ profileWriteBlocked = true
→ saveProfile() = false
→ localStorage上のschema 5データがそのまま残る

FUTURE_SCHEMA_DOWNGRADE_PROTECTION_OK

────────────────────
8. 日次計画もv97へ移行
────────────────────

今日のクエストのplanVersionを

v96 → v97

へ更新。

ensureTodayPlanSnapshot()は、
旧planVersionを見つけると未完了部分だけv97で再構築する。

完了済みslotは従来どおり固定。

したがってアップデート当日に
「朝に終えた復習が、更新後に未完了へ戻る」
ことを避ける。

────────────────────
11. 復帰対象を通常のMASTER候補より優先
────────────────────

nextMasterTopicCandidate()を変更。

従来:
stable → understood → review → learning → new

v97:
まず masteryHistory.recoveryNeeded を優先
その中で既存の状態順位・保持率を使う。

UIも、復帰対象では

「○○をMASTERへ」

ではなく

「○○をMASTERへ戻す」

と表示する。

復帰理由も状態に応じて変える。

- active review journeyあり
  → 復習ルートを完了
- dueあり
  → 期限/低保持問題を戻す
- 最低保持85%未満
  → 最低保持問題を優先
- 高次保持不足
  → 判断・適用を確認
- 章末統合不足
  → 章末直近70%以上へ戻す

「MASTERが消えたので教材から全部やり直す」設計にはしていない。

────────────────────
16. 今回やっていないこと
────────────────────

実ブラウザE2Eは未実施。
特に次は実機で最終確認余地がある。

- Safari / iOS PWAでIndexedDB復旧点が実際に4件保持されるか
- ブラウザのサイトデータ容量逼迫時の挙動
- Service Worker更新直後のv96→v97移行
- 複数タブ同時回答中の競合
- OSによるサイトデータ削除

v97では、これらが起きてもデータ損失を最小化する防御層を増やしたが、
ブラウザ自体がサイトデータ全体を削除した場合は、同じサイト領域内のIndexedDBも消える。

そのため外部JSON書き出しは引き続き最終防衛線。

────────────────────
17. 結論
────────────────────

v96までは
「学習設計として完成度を上げる」
ことが中心だった。

v97では初めて、
「数か月の学習履歴を預かるアプリ」
として保存設計を一段上げた。

現在
→ 一世代前
→ 長期復旧点 最大4
→ 外部JSON

の複数層になった。

さらに
旧schemaは段階移行し、
未来schemaは上書きしない。

MASTERも
「一度取ったら永遠」ではなく、
崩れたら必要な証拠だけ戻す状態として追跡する。

v96 → v97

長期利用・アップデート耐久性・MASTER復帰の横断監査を完了。
