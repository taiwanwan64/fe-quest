擬似言語の学び方

擬似言語（ぎじげんご）は、処理の手順を表すための記法です。IPAが定める共通の記述形式を理解し、問題ごとの注記も確認します。初めは短い処理から、実行前の値・実行した操作・実行後の値を結び付けて読む練習を進めましょう。

更新する値を決める代入では右側の式を今の値で計算し、その結果を左側へ保存します。読む値と書き換える場所を分けます。
次に進む場所を決める条件式が真か偽かを確かめ、分岐や繰返しの次の行を選びます。条件を調べる時点にも注意します。
呼出しの前後をつなぐ渡す引数と、呼出し先から戻った後に使う値を記録します。同じ変数名でも、どの処理の変数かを確かめます。

例：countの値が4のとき「count ← count + 3」を実行すると7になります。続く「count > 6」は、更新後の7を使うので真です。このように、次の判断へ渡す値を一つずつ確かめます。

記号の意味が曖昧なら、IPAの擬似言語の記述形式（用語・プログラム言語資料の別紙2）を確認してください。配列の要素番号やメソッドの仕様は、問題に書かれた前提に合わせます。演習後は、値が変わった理由を自分の言葉で説明してみましょう。
トレースを身につける練習法

短い処理で、解説を見る前の予想と、実際に追った結果を比べてみましょう。答えが違ったときは、最初に食い違った判断や更新を探します。分からない記号や操作は先に確認し、読める範囲から進めます。

結果を予想する入力と求める出力を確かめ、処理を終えたときの値を予想します。自信のない条件には印を付けておきます。
違いの理由を探す条件を調べた時点の値と、更新後の値を区別して追います。解説とは答えだけでなく、その値になった理由を比べます。
条件を変えて確かめる一つの入力を変え、動きがどう変わるかを先に説明します。繰返しなら、初めから条件が偽になる場合も試します。

練習例：整数のinitialを受け取り、次の処理が返す値と、nを更新する回数を考えます。

○整数型: advance(整数型: initial)
  整数型: n ← initial
  while (n < 5)
    n ← n + 2
  endwhile
  return n

initialが1なら、条件は1 < 5で真、更新後の3 < 5も真です。nは1 → 3 → 5と変わり、5 < 5が偽になって終了します。返す値は5、更新は2回です。

initialが5なら、最初の5 < 5が偽なので一度も更新しません。返す値は5、更新は0回です。同じ結果でも、そこに至る処理は異なります。

説明できた箇所を増やす練習後は、予想と違った理由を一文で残します。実コードのステップ実行を使う場合も、先に自分で予想し、どの操作を確かめたいかを決めてから比べましょう。

  再帰：呼出しごとの状態と、待っている処理を追う
  

    
再帰では、関数が自分自身を呼び出します。呼び出すたびに新しい実行が始まり、呼出し元は続きの処理を待ちます。関数名だけで追わず、各呼出しの引数・局所変数・戻る場所を記録します。

    

      
1. 戻り値が何を表すかを決める

      
品物を3個ずつのグループに分け、最後の不足分も1グループとして数える例です。初めのitemsは0以上の整数とします。groups(5)なら、3個と残り2個の2グループなので、戻り値は2です。

      
整数型: groups(整数型: items)
    if (items ≤ 0)
        return 0
    endif
    整数型: rest ← groups(items − 3)
    return rest + 1

      
itemsが0以下なら数えるグループはありません。それ以外は3個を1グループとして取り除き、残りのグループ数へ1を足します。最初は0以上でも、最後の呼出しで負の値になる場合があるので、停止条件は0以下を扱います。

    

    

      
2. 親の引数を変える処理と、新しい呼出しを分ける

      
groups(5)からgroups(2)を呼んでも、元の呼出しのitemsが2へ書き換わるわけではありません。この例の整数型の引数と局所変数は、呼出しごとに別々の状態として扱います。

      

        groups(5)で作られる3つの実行
        
呼出しその枠のitems先に必要な処理

        
          
① groups(5)5groups(2)の結果を待つ

          
② groups(2)2groups(−1)の結果を待つ

          
③ groups(−1)−1停止条件に入り0を返す

        
      

      
①のitems = 5と②のitems = 2を、同じ欄へ上書きして記録しません。配列やオブジェクトへの参照が渡される別の問題では、参照先を共有するかどうかも、その問題の定義で確認します。

    

    

      
3. 呼出し先が戻るまで、代入を待つ

      
rest ← groups(items − 3) では、まず右辺の関数を呼び、戻り値が得られてからrestへ代入します。待っている途中のrestへ、引数や推測した戻り値を先に書き込みません。

      
呼出し①はgroups(2)の結果を待ち、呼出し②はgroups(−1)の結果を待っています。③が0を返すと、②のrestへ0が入り、②は1を返せるようになります。

    

    

      
4. 戻った後の行を、保存していた枠で実行する

      

        戻り値が確定する順序：引数と戻り値は別の量
        
動作実行する枠確定する値

        
          
停止条件で返す③：items = −1戻り値0

          
②の代入を完了②：items = 2rest = 0

          
②から返す②：items = 2rest + 1 = 1

          
①の代入を完了①：items = 5rest = 1

          
①から返す①：items = 5rest + 1 = 2

        
      

      
戻る先は、呼出し元が待っていた代入の続きです。代入を終えた後に、その枠のreturnを実行します。①へ戻ったときのitemsは、最初に保存した5のままです。

    

    

      
5. returnで終わる経路では、後ろの行を実行しない

      
呼出し③は return 0 で終わるので、restを宣言・代入する行や、return rest + 1 を実行しません。戻り値0を使って続きを実行するのは、呼出し②です。

      
再帰呼出しの前にある処理は呼出し元が待ち始める前に実行され、後にある処理は呼出し先が戻ってから実行されます。出力問題でも、どの枠のどの行が実行されたかを記録してから表示順を読むと整理できます。

    

    

      
6. 停止条件に届くかを、引数の変化で確かめる

      
groups(6)は6 → 3 → 0と進み、groups(5)は5 → 2 → −1と進みます。どちらも0以下で止まります。停止条件をitems = 0だけにすると、5から始めた場合は0へ到達しません。

      
最初の入力範囲、1回でどれだけ変わるか、停止条件をセットで読みます。この例では正のitemsが毎回3だけ減るため、有限回で0以下になります。

    

    

      
7. 2つの再帰呼出しは、実行順に1つずつ完了させる

      
次は、長さwidthの区間を、各区間の長さが2以下になるまでほぼ半分へ分け、できた区間の個数を返す例です。最初のwidthは1以上の整数とします。

      
整数型: splitParts(整数型: width)
    if (width ≤ 2)
        return 1
    endif
    整数型: leftSize ← width div 2
    整数型: rightSize ← width − leftSize
    整数型: leftParts ← splitParts(leftSize)
    整数型: rightParts ← splitParts(rightSize)
    return leftParts + rightParts

      
divは整数の商です。splitParts(5)は長さ2と3へ分けます。最初のsplitParts(2)を完了し、leftParts = 1を保存してから、splitParts(3)を実行します。

      
長さ3は1と2へ分かれて2区間となるので、元の枠のrightParts = 2。最後に1 + 2 = 3を返します。後の呼出しを追っている間も、元の枠のleftParts = 1は保持されています。

      
長さ2の呼出しが2回現れますが、自動的に同じ結果を使い回すと決めつけません。このコードではその都度呼び出して1を返します。

    

    

      
8. 各枠に、引数・待ち場所・確定値を書く

      
呼び出すときは新しい枠へ引数を書き、呼出し元には「どの代入の結果を待っているか」を残します。戻ったら待っていた代入を完了し、その枠の次の行を追います。

      
確認するのは、すべての呼出しが停止条件へ届くこと、戻り値を受け取る枠が合っていること、次の呼出しを始める時点が合っていることです。FE QUESTの状態表示は、紙に予測を書いてから照合する補助として使えます。

4. ヒープ判定は、存在する枝を一つずつ調べる

  複数空欄：処理の目的と止まる条件から候補を確かめる
  

    
空欄の候補を選ぶときは、処理が満たすべき条件を先に書きます。短い例で間違いを見つけた後は、その原因を式や更新の役割へ戻して説明しましょう。一つの例が通っただけで、すべての入力に正しいとは決まりません。

条件と更新を組にする繰り返す条件と、その条件を変える更新を一緒に見ます。片方の候補を決めたら、もう片方と両立するか確かめます。

      
反例と理由を確かめる目的と違う結果や、終了しない入力を探します。残した候補では、繰返し中に何が減り、終了時に何が分かるかを説明します。

    

    
例：load件の作業を、1回に最大capacity件ずつ処理するときの回数を返します。loadは0以上、capacityは1以上の整数です。作業が0件なら0回とします。Aは継続条件、Bは残件数の更新です。

    
○整数型: batchCount(整数型: load, capacity)
  整数型: left ← load, count ← 0, take
  while ([A])
    take ← capacity
    if (left < take)
      take ← left
    endif
    left ← [B]
    count ← count + 1
  endwhile
  return count

    
Aは「left > 0」、Bは「left − take」です。残件数が正の間だけ処理し、その回に処理した件数を引きます。takeは残件数とcapacityの小さい方になるので、1以上の件数を処理して残件数を減らし、0になったら終了します。

  長文セキュリティの読み方
  

    
最初に、設問が「問題点」「追加で確認すること」「対策」のどれを求めているかを確かめます。本文を読むときは、書かれた事実、守るべき規則、まだ分からないことを短く分けてメモします。

    

      
事実を抜き出す誰の操作か、いつの記録か、どこに保存したかなど、設問に関係する記述を拾います。意図や被害を想像で足さないようにします。

      
条件と照合する権限・承認・保管などの規則と、実際の運用を比べます。登場人物の役割や、対象のシステムを取り違えないようにします。

      
根拠を添えて答える選んだ答えが、本文のどの記述と対応するかを確かめます。対策を問われたら、守る対象と実施する時点も合わせます。

    

    
例：規則は「申請者と承認者を別の人にする」、記録は「申請：R、承認：R、実行：T」です。規則に反する箇所を問われたら、申請と承認を同じRが担当している点が根拠になります。不正の目的や情報漏えいまでは、この記録から断定できません。

    
IPA公式公開問題で、選んだ答えと本文の根拠を結び付ける練習ができます。通信やデータの保管方法などが分からなければ、必要な関連知識を科目Aの教材で確認してから、同じ箇所を読み直しましょう。

  





        

  セキュリティ基礎：対象・権限・記録から対策を考える
  

    
設問が求める判断を確かめ、守る対象、利用する人、操作できる範囲、出来事の記録を結び付けます。対策の名称を見つけたら、その対策がどの条件へ働くかまで説明してみましょう。

    
1. 何を守り、どんな影響を減らすか

      
情報資産はデータだけでなく、サービスや機器なども含みます。脅威は害をもたらす原因、脆弱性は悪用され得る弱点です。弱点が利用されたときの影響を考えます。

      
機密性許可されていない相手への開示を防ぐ。
完全性内容が意図せず変わったり、壊れたりしないようにする。
可用性必要なときにサービスや情報を利用できるようにする。

      
情報が漏れたのか、内容が書き換わったのか、業務が止まったのかを分けると、対策の目的も整理できます。

    
2. 認証と、できる操作を分ける

      
認証は利用者や端末等を確かめること、認可はどの操作を許すかを決めることです。ログインできても、すべての情報へアクセスできるとは限りません。

      
知識の要素パスワードやPINなど、秘密として知っている情報。
所有の要素認証器を保持し、制御していること。
生体の要素指紋など、本人の身体的・行動的な特徴。

      
2要素認証では異なる2種類の要素を使います。確認画面が2回あることだけでは要素の種類は決まりません。同じパスワードを2回入力しても、種類は知識の1つです。

      
最小権限では、必要な操作・対象・期間へ許可を絞ります。職務分離では、作成と承認などの役割を分けます。両方の条件を満たしているか確かめます。

      
認証の詳しい要件は、NISTの認証ガイドラインで確認できます。

    
3. 情報が見えたり、操作されたりする場所を確かめる

      
端末、画面、机、出入口、記憶装置では、起こり得ることが違います。次の整理は対策の目的を読むためのものです。具体的な設定や有効な範囲は問題の条件に合わせます。
端末・物理対策の確認点
対策・仕組み確認すること
共有端末のログアウト・保存情報の管理前の利用者のセッションや保存した認証情報を次の人が使えないかを確認する。
クリアスクリーン／クリアデスク画面の情報を残したまま離席しない。机上の書類・媒体は別に片付けて保管する。
共連れ対策・アンチパスバック無認証の同伴入室を防ぐ対策と、入退室記録の順序を検査する仕組みを区別する。
ストレージ暗号化記憶装置からの読取りを保護する。起動済み端末の無断操作まで同じ対策で防げるとは限らない。
セキュアブート起動時に実行するソフトウェアを検証する。保存データの暗号化とは目的が異なる。
リモートワイプ端末へ命令が届く条件も含めて、遠隔消去が実行できるかを確認する。
クライアント認証・耐タンパ性許可した端末等の認証と、機器の解析・改造への耐性を区別する。
CAPTCHA自動処理への対策として使う。利用者が誰かを確定する認証とは区別する。

    
4. 接続と記録を一緒に読む

      
通信機器の名前だけで結論を出さず、接続先、許可する規則、検査する内容を確かめます。構成管理では、機器・ソフトウェアの種類や版を把握し、弱点の影響を受ける範囲へ結び付けます。
通信・接続の確認点
用語役割本文で確かめること
FW通信の許可・拒否送信元・宛先・ポート等の規則と、その通信が通る位置。
WAFWebアプリへの攻撃の検査・防御HTTP等の内容を検査できる構成と、対象のリクエスト。
IDS／IPS異常の検知／検知に加えた防御通知だけか、通信の遮断なども行うか。
DMZ公開用サーバ等を分離する領域どの区画間の通信を許可しているか。配置だけで安全性は決まらない。
プロキシ／リバースプロキシ要求や接続の代理・中継利用者側の外向き接続か、サーバ側への要求の受付か。
VPN離れた拠点・端末との通信路暗号化の範囲、接続先、認証・許可の条件。
BYOD個人所有端末の業務利用端末の管理、接続許可、業務情報の保存先。

      
ログを比べるときは、時刻の基準、時計のずれ、操作の対象も確認します。NTP等による時刻同期は時計を合わせる仕組みです。元の記録を残し、補正した理由も分かるようにします。

      
練習例：2台は同じ日・同じタイムゾーンで記録し、Rの時計だけが2分進んでいると確認できています。
時計のずれを補正した時系列
記録表示時刻確認された時計のずれ基準に合わせた時刻
端末Rの出力記録09:042分進んでいる09:02
端末Sの権限変更記録09:03ずれなし09:03

      
出力記録は基準時刻09:02なので、09:03の権限変更より前です。表示時刻だけの並べ替えでは逆になります。この2件だけでは、不正の意図や外部への漏えいは確定しません。

    
5. 被害を抑え、記録を残し、業務を戻す

      
不審な事象を見つけたら、組織の窓口やCSIRT（インシデント対応チーム）へ伝える情報を整理します。被害拡大の抑制と、調査に必要な記録の保全を考えます。デジタルフォレンジックスは、デジタル証拠の収集・保全・分析に関わります。

      
切断、停止、再起動、消去などは、業務や調査へ異なる影響があります。設問にある手順・権限・優先事項へ照合します。電源断ではメモリ上の情報が失われるため、その影響も考えます。

      
復旧に使うバックアップは、攻撃や災害で同時に失われにくい保管と、復元できるかの確認が必要です。隔離した保管先、変更されにくいコピー、場所の分散などを条件に応じて組み合わせます。

      
対応の考え方は、NISTのインシデント対応資料でも整理されています。実際の操作は組織の対応手順に従います。

    
6. 運用が続く仕組みを確認する

      
内部不正を考える際の動機・プレッシャ、機会、正当化は、対策を整理するための観点です。本文にない個人の意図を断定する根拠にはしません。権限の見直しや別担当者による確認は、実行できる機会へ働く対策です。

      
アカウントの終了・権限の変更・設定の例外を見直し、記録と責任者を対応させます。予防、発生時の対応、復旧、改善のどれを求める設問かも確かめます。

      
IPAの内部不正防止ガイドラインで、組織の管理や運用の観点を確認できます。

  






        

  セキュリティ演習：条件と根拠を対応させて判断する
  

    
ここでは3つの架空の練習例を使います。問い、本文にある条件、そこからいえる結論を対応させましょう。危険があり得ることと、被害が実際に起きたことも分けて考えます。

    
1. 変更で誰が何をできるようになるか

      
変更前は、本人認証を受け、許可されたIDだけが報告書を取得できます。変更後は、推測困難な共有リンクを知る人が本人認証なしで取得できます。リンクは発行から48時間未満の間だけ有効で、管理者が途中で失効できます。以下の相手は、変更前の取得許可を持たないものとします。
共有リンクを導入した前後の取得可否
条件変更前変更後根拠
リンクを知り、発行から24時間、失効なし不可可本人認証を受けていない相手でも閲覧できる範囲が増える。
リンクを知らない不可不可リンクを持たない相手まで閲覧できるとはいえない。
リンクを知り、発行から48時間不可不可有効期間が終了しており、新しい取得はできない。
リンクを知るが、管理者が失効済み不可不可失効後の新しい取得はできない。

      
新たに確認するのは、有効なリンクの転送等によって許可外の相手が取得できる経路です。リンクが推測困難であることと、入手した人の本人確認があることは別です。実際の漏えいが起きたとは、この説明だけから断定できません。

      
この例では、すでに取得したコピーを失効操作で消去する機能はありません。新しい取得を止めることと、取得済みの情報を回収することを分けます。

    
2. 人と操作と対象を対応させる

      
帳票の作成担当Uは自分の下書きを閲覧・編集できます。確認担当Wは帳票を閲覧し、Uの帳票を承認できますが、編集はできません。設定担当Tはシステム設定だけを担当し、業務上の閲覧・承認権限を持ちません。
この例で認める操作
担当帳票の閲覧下書きの編集帳票の承認システム設定
U：作成担当可可（自分の下書き）不可不可
W：確認担当可不可可（Uが作成した帳票）不可
T：設定担当不可不可不可可

      
Uの自己承認を認めないことは職務分離、Tへ業務上の権限を広げないことは最小権限の確認になります。ログにTの設定変更があっても、帳票を閲覧した記録だと読み替えません。

    
3. 問題の箇所と担当を結び付ける

      
共有サービスの業務ルールは総務G、共有・認可設定は情報システムT、ホストOSの保守は提供者Pが担当する契約です。この分担を根拠として、まず確認する担当を選びます。
この契約で確認する担当
問題の箇所担当契約にある根拠
共有期限の業務ルールが決まっていない総務G業務上の承認・期限ルールを決める担当。
決めた期限を過ぎても共有設定が有効情報システムT共有・認可の設定を運用する担当。
提供者が保守するホストOSの弱点提供者Pこの契約でホストOSを保守する担当。

      
サービス名や「クラウド」という語だけで全部同じ担当にしません。SaaS・PaaS・IaaSは提供範囲を考える手掛かりですが、具体的な部品、設定、データの責任は、問題の契約・運用条件へ照合します。別の契約へこの表をそのまま当てはめることはできません。

    
4. 結論に足りない条件を探す

      
「リンクがあるので全員に漏えいした」「設定担当が操作したので帳票を読んだ」のような結論には、入手・取得の記録や操作対象の根拠が足りません。確認できた事実と、追加で調べることを分けます。

      
問いへ戻る新しく増える経路、違反した規則、対処する担当のどれを求めるかを確認します。
根拠を一つずつつなぐ本文の条件と選択肢の主語・操作・対象・時点を照合します。途中の関係を想像で補わないようにします。
