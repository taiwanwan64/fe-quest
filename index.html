擬似言語の学び方

科目Bでは特定のプログラム言語の文法暗記より、「この処理で何が行われているか」を読み取る力を優先します。擬似言語は問題文で示される記述形式を読み、処理を追うことが中心なので、JavaやPythonなど一つの言語の文法を丸暗記する必要はありません。

トレースを身につける練習法

科目Bでは、コード全体を先に説明しようとするより、実行した行と値の変化を順番に追う方が確実です。解説を読んだ直後も、初期値を少し変えてもう一度追うと「答えの暗記」ではなく処理の理解になります。

① 実行した行今どの行を処理したかだけを1行ずつ記録します。
② 条件の真偽分岐・繰返しは T / F を書き、次に進む行を決めます。
③ 変わった値変数・配列のうち、更新されたものだけを書き換えます。
定番アルゴリズムも丸暗記しない名前や完成形を覚えるだけでなく、「比較した後にどの値がどう動くか」を説明できる状態を目標にします。実コードのステップ実行は確認用の補助として使えますが、特定のプログラム言語を習得していなくても擬似言語のトレースは練習できます。
文法早見表：変数・条件分岐・繰返し・関数

擬似言語は、プログラムの処理を読み取るための表記です。まずは「変数の値がどう変わるか」を1行ずつ追えるようにします。

1. 変数と型

文字型1字の文字を格納します。
文字列型複数の文字を格納します。
整数型整数を格納します。
実数型整数と小数を格納します。
論理型true（真）またはfalse（偽）を格納します。
未定義まだ値が格納されていない状態です。
整数型: a a ← 1 f ← e + 2

「←」は右側の計算結果を左側へ格納する代入です。プログラムは原則として上から下へ1行ずつ実行します。

2. 演算子を日本語と結び付ける

種類表記意味
算術演算子+ / - / × / ÷ / mod加算 / 減算 / 乗算 / 除算 / 剰余
関係演算子> / ≥ / < / ≤ / = / ≠より大きい / 以上 / より小さい / 以下 / 等しい / 等しくない
論理演算子and / or両方が真 / どちらか一方でも真

「5以上」には5を含みますが、「5より大きい」には5を含みません。境界値を含むかどうかまで読みます。

3. if・elseif・else

if条件が真なら直後の処理を実行。偽ならその処理を飛ばします。
elseif / else前の条件が偽なら次の条件を確認し、どれも当てはまらなければelseへ進みます。
if a = 6 a ← a + 1 elseif a = 5 a ← a - 1 else a ← a + 3 endif

条件を一つずつ判定し、最初に真になった分岐だけを実行します。

4. whileとdoは「条件を調べる位置」が違う

while先に条件を確認します。最初から偽なら、処理を1回も実行しません。
do先に処理を実行し、その後で条件を確認します。最初から偽でも1回は実行します。
while 0 > 0 処理 endwhile do 処理 while 0 > 0

繰返しの中で条件がいつまでも偽にならないと、処理が終わらない「無限ループ」になります。

5. forは4つに分けて読む

for変数→初期値→条件式→増減
for (i を 1 から 3 まで 2ずつ増やす) 処理 endfor
① 初期値を格納→② 条件を確認→③ 本体を実行→④ 増減↺

初期化は最初の1回だけです。その後は、条件判定→本体→増減→条件判定…を繰り返します。

6. 関数・手続・有効範囲

関数引数を受け取り、処理後にreturnで戻り値を呼び出し元へ返します。
手続戻り値を返さない処理のまとまりです。
局所変数・引数宣言された関数や手続の中だけで利用し、終了すると値は残りません。
大域変数プログラムの広い範囲から利用し、各処理が終了しても値を残して再利用できます。
引数を持って呼出し→引数へ値を格納→関数内を実行→returnで戻る

7. トレースは「変化した状態」を書く

変数ごとに列を作る値の変化を横に混ぜず、追う対象を分けます。
1行ずつ実行する飛ばし読みせず、現在値を使って次の値を求めます。
値が変わらない行は省略else、endif、endwhile、do、endforなどは、値が変わらないため表への記入を省略できます。
条件式は記号で短く「aが5より大きい」は「a > 5」のように書くと速く確認できます。

FE QUESTの「状態」欄は、このトレース表を画面上で可視化したものです。慣れてきたら、問題文を見て自分で小さな表を書いてから答えを予測してみてください。

再帰トレース：呼出しと戻りを分けて追う

再帰は、処理の途中で自分自身をもう一度呼び出す書き方です。難しく見える原因は、同じ関数名・同じ変数名が何度も出ることです。1回の大きな処理として追わず、呼出しごとに別の実行として分けます。

1. 同じ関数でも、呼出しごとに引数は別

procedure rec(n) if n = 1 return endif rec(n - 2) n を出力 endprocedure
rec(5)この呼出しの n = 5
rec(3)この呼出しの n = 3
rec(1)この呼出しの n = 1

変数名は全部nでも、値は共有しません。FE QUESTの「スタック」表示でも、呼出しが増えるたびに別の実行状態が積み重なっていると考えます。

2. まず停止条件まで「内側へ」進む

最初に確認するのは、再帰を止める条件です。FE QUESTではこれを基底条件と呼ぶことがあります。

rec(5)→rec(3)→rec(1)→return

停止条件へ近づくように引数が変化しているかも確認します。停止条件へ到達しない再帰は終わりません。

3. 内側が終わったら、呼出し元の「次の行」へ戻る

呼出し方向
rec(5) → rec(3) → rec(1)
呼出し先を先に実行
↔
戻り方向
rec(1) → rec(3) → rec(5)
呼出しの次の行から再開

上の例では、rec(1)がreturnしたあと、rec(3)の「nを出力」へ戻ります。その次にrec(5)の「nを出力」へ戻ります。

再帰呼出しの下にある処理は、すぐには実行されません。呼出し先が最後まで終わってから実行されます。

4. 再帰呼出しの「前」と「後」で出力順が変わる

procedure p(n) if n = 0 return endif n を出力 p(n - 1) n を出力 endprocedure
呼出し前の出力内側へ進む途中で実行されるので、3 → 2 → 1 の順。
呼出し後の出力外側へ戻る途中で実行されるので、1 → 2 → 3 の順。

p(3)なら全体の出力は「3 2 1 1 2 3」です。「どの行が再帰呼出しより上か下か」を見るだけでも順序を予測できます。

5. 戻り値は、最も内側から1段ずつ外へ返す

function sum(n) if n = 1 return 1 endif return n + sum(n - 1) endfunction
sum(1)=1→sum(2)=2+1→sum(3)=3+3→sum(4)=4+6

呼出し順は外側から内側ですが、戻り値の計算は内側から外側です。呼出し順と戻り値の確定順を同じ向きに書かないようにします。

6. 「a ← r(x - 1)」は2段階で読む

① r(x - 1)を呼ぶ→② 戻り値を待つ→③ aへ代入

再帰関数が戻るまではaへの代入は完了しません。関数呼出しと代入を一度に処理しようとせず、先に呼出し先を最後まで追います。

7. 自分自身を2回呼ぶなら、上の呼出しを終えてから次へ

a ← r(x - 1) b ← r(x - 2) return a + b
順番実行するものその時点のポイント
1r(x - 1)この再帰呼出しを最後まで完了する。
2aへ代入返ってきた値をaへ保存する。
3r(x - 2)次の再帰呼出しを最後まで完了する。
4bへ代入 → a + b両方の戻り値がそろってから加算する。

枝分かれ図を一気に頭の中で展開しないでください。実際の実行順は上から1行ずつです。左側の呼出しが終わってから次の行へ進みます。

8. トレース表は「呼出し1回＝1つの枠」で作る

① 呼出しごとに枠を分ける同じnやxでも、別の呼出しなら別の値として記録。
② 停止条件まで進むまず内側へ進み、どこでreturnするかを確定。
③ 戻る場所を書く呼出し元の「再帰呼出しの次の行」へ戻る。
④ 戻り値を外側へ渡す代入や計算がある場合は、戻ってから実行する。

再帰が苦手なときは、コード全体を何度も読み直すより、呼出しごとに小さなトレース表を分ける方が安全です。

木構造：図と一次元配列を行き来する

木構造の問題は、図そのものより「親子関係」と「配列の要素番号」を対応させられるかが重要です。まず用語と形を確認し、その後に配列へ変換します。

自分の手番子の評価値の最大値を親へ戻す。
相手の手番子の評価値の最小値を親へ戻す。

⑦ 状態を1行ずつ更新共有参照なら、同じ実体を指す他の変数からも変更後の状態が見える。

迷ったら「変数の箱」ではなく「インスタンスの箱」を描き、変数から矢印を伸ばします。共有参照の問題がかなり追いやすくなります。

連結リスト：値ではなく参照の矢印を付け替える

連結リストは、要素を物理的に横へ並べるのではなく、各要素が持つ「次の要素への参照」で順番を作ります。科目Bでは値より先に、head・現在位置・nextの矢印を追うと安定します。

1. 1要素は「値 + 次への参照」

head→ Anext: B→ Bnext: C→ Cnext: null

head は先頭要素への参照です。現在位置を p とすると、p ← p.next で次の要素へ移動します。

終端は問題によって null、未定義など表記が異なります。意味は「次にたどる要素がない」です。問題文の表記に合わせます。

2. 挿入は「後ろを保存してから、前をつなぐ」

A→Cの間へ新しいBを入れるなら、後続のCへの道を先にBへ持たせます。

① B.next ← A.next ② A.next ← B
A→ B→ C

順序を逆にして、先に A.next ← B とした後で B.next ← A.next と読むと、その時点のA.nextはBなので、Bが自分自身を指す形になり得ます。右辺が「更新前の参照」を必要としていないかを確認します。

3. 削除は「飛び越すように前のnextを書き換える」

A→B→CからBを外すなら、Aから見た次の行き先をBの次へ変更します。

prev.next ← target.next
A→ C

配列の削除のように後ろの要素を一つずつ詰めません。連結リストでは、基本は参照の付替えです。

4. 先頭だけはhead自身を書き換える

先頭へ追加新要素.next ← head の後、head ← 新要素。
先頭を削除head ← head.next。前の要素がないためheadを直接更新。

中間要素なら「前の要素.next」を変えますが、先頭には前の要素がありません。そこでheadが特別扱いになります。

5. 末尾や位置指定ではprevとptrを2本で追う

ptr
今見ている要素
prev
ptrの一つ前の要素
prev ← ptr ptr ← ptr.next

この2行をセットで進めると、ptrが目的の位置や末尾へ到達したとき、prevからリンクを付け替えられます。

末尾削除は「末尾を見つける」だけでは足りません。単方向リストでは、末尾の一つ前の要素を覚えておく必要があります。

6. 空・1要素・見つからない場合を先に確認

状態見るポイント典型的な処理

見つからない終端まで到達リストを変えず終了

7. 「リストから外れた」と「実体が消えた」は別

リンクの付替えである要素へheadから到達できなくなれば、その要素はリストの並びからは外れています。ただし、トレースでは「矢印がなくなった」ことと「インスタンスそのものを消去した」ことを同じ意味にしません。

別の変数がそのインスタンスを参照しているなら、その変数からは引き続き参照できます。リストの順序は、あくまでheadから参照をたどって到達できる要素で判断します。

8. 双方向リストは前後2本の矢印

next次の要素への参照。head側から順方向へたどる。
prev前の要素への参照。tail側から逆方向へたどれる。

双方向リストでは、挿入・削除時に片側だけ更新すると参照関係が壊れます。問題文でnextとprevの両方がある場合は、前向き・後ろ向きの両方を確認します。

① headを確認空か、先頭はどれか。
② 現在の矢印を書く値より先にnextの接続を図にする。
③ 右辺を先に読む更新前の参照が必要なら先に保存。
④ 代入後の矢印を書き直す古い矢印を残さない。
⑤ prev / ptrを別欄で追う現在位置と直前位置を混同しない。
⑥ 境界条件を見る空・先頭・末尾・1要素・未発見。

リスト問題は「値の並び」を暗算するより、代入1回ごとに矢印を描き直す方がミスを減らせます。

スタック・キュー：出し入れする端を固定して追う

スタックとキューは、どちらも「値を入れて、あとで取り出す」データ構造です。違いはどちら側から取り出すか。図の向きで覚えず、スタックならTOP、キューならFRONT / REARを最初に書いてから追います。

1. スタックはLIFO = FILO

LIFOLast In, First Out。最後に入れた値が最初に出る。
FILOFirst In, Last Out。最初に入れた値が最後に出る。

言い方は違いますが、表している動作は同じです。

底 ABC TOP

A → B → C の順にpushしたなら、最初のpopはCです。

peek()TOPTOPの値を返す変えない

popとpeekは返る値が同じに見えることがありますが、popだけがスタック本体を変えます。

3. キューはFIFO。追加と取出しで端が違う

A → B → C の順にenqueueしたなら、最初のdequeueはAです。enqueueはREAR側、dequeueとpeekはFRONT側と固定して追います。

6. 優先度付きキューは「FIFOだけ」では決めない

優先度付きキューでは、通常のキューのように単純な到着順だけで取り出しません。まず問題文の優先度規則を確認します。

例：小さい優先度値ほど高い、と問題文で定義 A(優先度3) B(優先度1) C(優先度2) D(優先度1)

優先度1が必ず高い、とは決めつけません。優先度の大小や同優先度時の順序は、問題文に書かれた定義を使います。

8. 循環キューは「配列上の位置」と「キューの順番」を分ける

固定長の配列をキューとして繰り返し使う方式では、末尾まで進んだ位置が先頭へ戻ります。これを循環キュー（リングバッファ）として扱います。

head / front次に取り出す要素の位置。dequeue後に前へ進む。
tail / rear次に追加する位置。enqueue後に前へ進む。
size / count現在入っている要素数。空と満杯の判定に使われることがある。
配列上: [ E ][ B ][ C ][ D ] 論理順: B → C → D → E ↑head tailは先頭側へ回り込む

head == tail だけで「空」と決めつけないでください。実装によってはsize/countや別の条件で空・満杯を区別します。判定式は問題文のコードをそのまま使います。

トレース表には「head・tail・size」と、書き換わった配列要素だけを残すと追いやすくなります。

9. 後置記法は「演算子が来たら2個pop」で追う

後置記法（逆ポーランド記法）では、数値などのオペランドをスタックへ積み、演算子が現れた時点で必要な値を取り出して計算します。

オペランドそのままpushする。
演算子右オペランド、左オペランドの順にpopする。
計算結果左 op 右を計算してpushし直す。
8 3 - push 8 → push 3 → 「-」 右 = pop() → 3 左 = pop() → 8 8 - 3 = 5 → push 5

減算と除算はpopした順のまま計算すると逆になります。最初のpopが右、次のpopが左と固定して追います。

式を最後まで読んだとき、スタックに計算結果が1個だけ残るかを最終確認に使えます。

ビット列：桁をそろえて、演算ごとに1行ずつ書き換える

ビット列の問題は、10進数の暗算へ逃げずに固定されたビット数・各桁の位置・演算後のビット列を1行ずつ追うのが基本です。まず桁をそろえ、AND / OR / XOR / シフトを一つずつ適用します。

1. 基数変換は「10進数へ」と「10進数から」で方法を分ける

別の基数 → 10進数各桁 × 基数の重みを足す。右端は基数の0乗。
10進数 → 別の基数変換先の基数で0になるまで割り、余りを下から上へ読む。
10110₂ = 1×2⁴ + 0×2³ + 1×2² + 1×2¹ + 0×2⁰ = 22₁₀

科目Bで演算途中に10進数との対応を確認したくなったら、この2手順だけを短く使います。

2. 8ビットなら、常に8個の箱として見る

最上位 0001 0100 最下位

4ビット・8ビットなど固定長が指定されている問題では、桁数を途中で変えません。論理演算も加減算も、右端をそろえて縦に並べるとミスしにくくなります。

3. 加算・減算は繰上がり／繰下がりを別に書く

加算1+1=10₂。下の桁へ0を書き、上の桁へ1を繰り上げる。
減算0から1を引けないときは、上位から10₂を借りて計算する。
00001111 + 00000001 ---------- 00010000

固定8ビットなら、9桁目へあふれたビットをどう扱うかは問題文の条件に従います。勝手に桁数を増やしません。

4. 2の累乗で割ると、下位ビットが剰余になる

除数が 2ⁿ なら、下位nビットが剰余、その左側が商として読めます。

10101101₂ ÷ 8 8 = 2³ なので下位3ビットを見る 10101 | 101 商 剰余 商 = 10101₂ 剰余 = 101₂

「2の何乗で割っているか」を先に確認すると、どこでビット列を分けるか決まります。

5. AND / OR / XORは「マスクの1が何をするか」で覚える

操作マスクが1の位置代表用途
A AND maskAの値を残す必要なビットだけ取り出す

A XOR maskAを反転する特定ビットを反転する

7. 論理シフトは、空いた場所へ0を入れる

論理左シフト左へ1ビットなら2倍相当。空いた右側へ0を入れる。
論理右シフト右へ1ビットなら半分相当。空いた左側へ0を入れる。
00000110 << 2 → 00011000 00011000 >> 2 → 00000110

「左へ1ビットなら必ず2倍」とは限りません。固定長で左端から1があふれれば、そのビットは捨てられるためです。

8. 複数演算は、1行ごとに結果を書き直す

x ← x AND mask x ← x >> 1 x ← x XOR toggle x ← x OR setMask

最後だけを暗算せず、各行の直後のxを書きます。次の演算は一つ前の結果に対して行うため、途中結果を飛ばすと崩れやすくなります。

9. 符号化は「データ部を取り出す → ひな形へ埋める」で追う

UTF-8のように、決まったビットパターンへ元データを分割して埋め込む処理では、数値の意味を一度に考えず、元データのビット列と出力用のひな形を分けて追います。

① ひな形を固定先頭の固定ビットと、データを入れる位置を先に区別する。
② 下位側から分ける必要なビット数ずつ、元データの下位側から取り出す。
③ ORで埋める固定ビットを壊さず、空いているデータ部分へ値を重ねる。
例: 3バイト形式のひな形 1110xxxx 10xxxxxx 10xxxxxx ↑ ↑ ↑ データを入れる位置だけを使う 元データを必要な幅に分ける → 各ブロックを対応する x の位置へ埋める → 固定の 1 / 0 はそのまま残す

「何ビット左へ動かすか」「何で割った余りを使うか」は、データをどの幅で切り出すかから決まります。候補式を先に暗記しない方が安全です。

UTF-8固有の値を覚えるより、固定ビットと可変ビットを分離し、切り出したデータを所定位置へ戻す手順を理解しておくと、類似のビット詰め問題にも対応できます。

8. 選択肢は最後に照合する

空欄問題で最初から各選択肢を総当たりすると、途中状態が増えて混乱しやすくなります。まずコードから必要条件を作り、その条件を満たす選択肢を最後に探します。

前から追う初期値が明確なら、空欄直前までの状態を作って候補を評価。
後ろから絞る空欄後の条件や最終値が強い手掛かりなら、必要な値を逆算。

「この選択肢なら何となく合いそう」と状態を選択肢へ寄せないこと。トレース結果と一致する候補を選びます。

9. 総合問題のチェック順

① 仕様を読む配列番号、未定義値、メソッドの意味を確認。
② 状態欄を作る変数・配列・戻り値・参照を必要最小限で表にする。
③ 呼出しを小さく分解関数やメソッドの戻り値を先に確定。
④ 代入ごとに更新古い値を残さない。
⑤ 分岐条件を再判定更新後の値でif / whileを評価。
⑥ 最後に選択肢照合自分の状態表と一致するものを選ぶ。

総合問題ほど「全部を頭の中で処理しない」ことが重要です。部品に分け、途中状態を外へ書き出すほど安定します。

実戦トレース：1行ずつではなく「状態が変わる単位」で追う

長いプログラムでは、全変数を毎行書き写すより、比較・代入・参照移動・関数の戻りなど、状態が変わる場所へ絞って記録すると速く追えます。

① 仕様を固定配列の開始番号、整数除算、未定義値、関数の戻り値などを先に確認。
② 変化点だけ記録値が変わらない行は結果だけ確認し、表へ同じ値を何度も書かない。
③ 呼出し先を完了関数・再帰は呼出し先の戻り値が決まってから、呼出し元の次の行へ戻る。
④ 参照は矢印で追うリストは値のコピーではなく、どの要素を指すかを更新前・更新後で描く。
⑤ 反復は区切る外側ループ1回、探索範囲1回など、意味のある1周ごとに状態をまとめる。
⑥ 最後に選択肢途中状態を作ってから候補と照合し、選択肢に合わせてトレースを曲げない。
途中表の列は「必要になった変数だけ」最初から大きな表を作る必要はありません。条件式で使う値、更新される値、最終結果へ影響する値を中心に列を増やします。
複数空欄：全部を同時に考えず「役割 → 依存関係」の順で解く

空欄が複数ある長いプログラムでは、候補を組み合わせて総当たりすると急に重くなります。まず各空欄が何を決める場所かを言葉にし、ほかの空欄へ影響する順に確定します。

① 空欄の役割を一言で書く「ループの終了条件」「次に見る要素」「戻り値」など、式そのものより先に役割を決める。
② 前後の確定部分を使う空欄の直前に何が分かっていて、直後で何に使われるかを見る。離れた行まで一度に追わない。
③ 依存する空欄は後回し別の空欄で決まる値を使うなら、元になる空欄から先に解く。空欄番号の順とは限らない。
④ 境界値で壊れないか確認最初・最後の要素、0回目・1回目、空や末尾など、条件が切り替わる地点を小さく試す。
⑤ 1ケースだけ手で通す候補を絞ったら短い入力で一周だけ実行し、更新順・添字・参照先が意図どおりか確認する。
⑥ 最後に全体へ戻す個々の空欄が局所的に正しくても、全体の目的を満たすかを最後に確認する。
空欄番号は「解く順番」ではありません先に確定できる条件や、ほかの処理の前提になる空欄から解くと、組合せを総当たりせずに済みます。

科目Bの情報セキュリティは、セキュリティ用語だけで完結しません。ネットワーク・クラウド・データベースなど、科目Aのテクノロジ分野の知識も組み合わせて判断します。

長文だからと捨てず、文章中の手掛かりを拾う練習をします。公式公開問題も早めに見て、長さとレベル感に慣れておくのが有効です。
セキュリティ長文：事実 → 守る対象 → 根拠 → 対応の順で読む

科目Bのセキュリティ問題は、知っている用語を選ぶだけではなく、今どの段階で、何を守るために、どの証拠を根拠として、何をするかを判断します。対策名より先に、時系列と目的を整理します。

1. インシデント初動は「封じ込め」と「証拠保全」を両立する

報告→ 隔離→ 証拠保全→ 影響調査→ 除去・復旧→ 再発防止

CSIRTは、組織内でセキュリティインシデントへ対応するチームです。デジタルフォレンジックスは、端末やログなどのデジタル証拠を収集・保全・分析する考え方です。

不審端末をネットワークから切り離すことは、被害拡大を抑えながら端末上の情報を残しやすい初動です。

手順を確認せず電源断・再起動・初期化をすると、メモリ上の情報やログなど、調査に必要な証拠を失う場合があります。

2. 「何が危ない？」は資産・脅威・脆弱性に分ける

情報資産守る価値があるデータ、システム、端末、知識など。
脅威情報資産へ悪影響を与える攻撃・災害・誤操作など。
脆弱性脅威に悪用され得る弱点。未修正ソフトや設定不備など。
機密性許可された人だけが情報へアクセスできる。
完全性情報が正しく、勝手に改ざんされていない。
可用性必要なときに利用できる。

OS・ミドルウェア・アプリの名称とバージョンを構成管理しておくと、脆弱性公表時に「どの端末が影響を受けるか」を素早く絞れます。

3. 認証は「何回」より「何要素」を見る

知識パスワード・暗証番号など、本人が知っているもの。
所有物スマートフォン・ICカードなど、本人が持っているもの。
生体指紋・顔・虹彩など、本人の身体的・行動的特徴。
方式見るポイント例
2要素認証異なる2要素を使うパスワード＋スマートフォンの認証アプリ
2段階認証認証を2段階で行う。要素が異なるとは限らない同じ知識要素を2回確認する方式もあり得る

「2回認証したから2要素」とは限りません。知識・所有物・生体のどの要素を使っているかで判断します。

4. 最小権限と職務分離は、守り方が違う

最小権限一人の利用者へ、業務に必要な最小限の権限だけを与える。
職務分離申請・承認・実行などを複数人へ分け、一人だけで不正を完結しにくくする。

「権限が広すぎる」なら最小権限、「申請者が自分で承認できる」なら職務分離を疑います。

5. 端末・入退室・紛失対策は「何を防ぐか」で区別する

対策主に防ぐもの

6. ログは「誰が・いつ・何をしたか」を時系列でつなぐ

認証成功・失敗、操作対象、権限変更、外部通信などを、複数の機器から突き合わせて調査します。

時刻同期NTPなどで機器の時計を合わせる。時刻がずれると出来事の前後関係を判断しにくい。
ログ保全調査前に消去・改ざんしない。必要ならアクセス制御や別保管で証拠性を保つ。

一つのログだけで断定せず、認証・通信・端末・アプリのログを時間軸で合わせます。

7. バックアップは「取る」だけでなく「生き残る・戻せる」まで

ランサムウェア対策常時接続の場所だけに置かず、隔離・オフライン・変更されにくい保管先も組み合わせる。
災害対策同じ建物だけに置かず、同時被災しにくい場所へ分散する。

復元テストを行い、実際に戻せることまで確認します。バックアップが存在しても、復元できなければ復旧手段になりません。

8. 内部不正は「動機・機会・正当化」に分けて読む

動機・プレッシャ不満、金銭問題、過大な目標など、不正へ向かう理由。
機会権限が広すぎる、監視がないなど、不正を実行できる状況。
正当化「自分は悪くない」など、不正を自分の中で合理化する考え。

問題では、どの要因を減らす対策かを見ます。最小権限・職務分離・ログ監視は、特に「機会」を小さくする方向の対策です。

10. 選択肢を見る前に「何の段階を聞いているか」を決める

事象の特定何が起きたか。フィッシング、マルウェア、不正アクセスなど。
初動被害拡大を止め、報告し、証拠を残す。
調査ログ・設定・構成情報を突き合わせて原因と範囲を確認。
復旧脅威を除去し、安全を確認して業務を戻す。
再発防止権限、教育、設定、パッチ、監視などを改善する。
平時の予防バックアップ、構成管理、MFA、最小権限などを事前に整える。

選択肢の対策自体が正しくても、設問が「最優先の初動」を聞いているのに再発防止策を選ぶと不正解になり得ます。

セキュリティ問題演習：変わった条件と責任範囲だけを追う

長文のセキュリティ問題では、書かれている危険を全部探すのではなく、設問が聞いている変化・利用者・システムの層・責任範囲だけを切り出します。選択肢を読む前に、問題文の因果関係を短く図にします。

1. 「導入したら増えるリスク」は変更前との差分だけを見る

変更前→新しい運用→増える接続・端末・権限→増加するリスク

たとえば私物PCからVPN接続を許可するなら、私物PCのマルウェアが社内へ到達する経路や、VPN接続数の増加による可用性への影響は「変更によって増えるリスク」です。

もともと存在していた紛失リスクや、変更内容と関係のない人の操作を選んでも、「今回の変更で増えるリスク」にはなりません。

2. リスクは「攻撃が成立する鎖」が全部つながるか確認する

攻撃者ができること→利用できる設定・経路→守る対象へ到達→被害

送信元アドレスや初期設定が公開されていて、利用者がその送信元を信頼する運用なら、なりすましメールが成立する可能性があります。逆に、途中の条件が一つ成立しない選択肢は除外します。

「攻撃名が有名だから」ではなく、問題文の条件だけで攻撃経路が最後までつながるかを見ます。

3. ID・パスワードは「どの層の認証か」を分ける

層例確認すること
端末 / OS共有PCへログインする端末ID・パスワード端末を誰が使えるか
ブラウザ保存されたID・パスワード、オートコンプリート次の利用者へ認証情報が残らないか
業務アプリ個人別の利用者ID・パスワード誰の権限で業務データへアクセスするか

「利用者IDを共有していない」と書かれていても、それが業務アプリのIDだけを指すなら、共有端末のOS認証やブラウザ保存情報は別問題です。

同じ「ID」「パスワード」という言葉が出たら、端末・ブラウザ・アプリのどれかを横にメモします。

4. 権限表は役職名ではなく、業務手順から埋める

入力する人入力権限が必要。自分で承認する必要があるとは限らない。
承認する人承認権限が必要。内容確認のため閲覧権限も必要になりやすい。
管理者設定変更権限があっても、業務上の承認者とは限らない。
委託先契約・要求事項で許された作業だけを行う。委託元と同じ権限とは限らない。

「入力した人とは別の人が承認する」というルールなら、入力と承認を分離します。まず業務フローを書き、その後で権限表へ○を置きます。

「課長だから全部できるはず」「システム部だから承認できるはず」のように、肩書だけから権限を推測しません。

5. クラウドの責任は「会社」ではなく「管理している層」で切る

問題がある層まず確認する責任範囲
クラウド基盤・PaaSが提供するDBMSやミドルウェアサービス提供者が管理する範囲か
利用者が作ったWebアプリのプログラム開発・運用担当が管理する範囲か
業務上の利用方法・データ・アカウントサービス利用組織が管理する範囲か

「PaaSだから全部クラウド事業者」「委託しているから全部委託先」と決めつけません。脆弱性がどの部品にあるかを先に特定し、その部品を管理する主体へ結び付けます。

6. 選択肢は一文ずつ「根拠があるか」を判定する

主語その人・組織が本当に問題文に登場し、その操作をする立場か。
行為その設定・接続・権限が問題文で許可されているか。
経路被害対象まで実際に到達できる構成か。
結果その行為から本当に機密性・完全性・可用性への影響が生じるか。

選択肢の一部だけ正しくても、後半の因果が問題文とつながらなければ不正解です。一文を「主語 → 行為 → 経路 → 被害」に分解すると見抜きやすくなります。

7. 長文問題ではこの順でメモする

① 変更点→② 利用者 / 組織→③ 接続・認証・権限→④ 管理責任→⑤ 選択肢照合

文章の細部を全部覚える必要はありません。設問に必要な関係だけを5項目へ圧縮すると、長文でも判断材料が見えやすくなります。
