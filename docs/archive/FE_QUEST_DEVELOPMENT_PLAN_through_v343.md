## 1. プロダクトの北極星

FE QUEST は、基本情報技術者試験の単なる問題集ではなく、**学習者の実際の状況から「今日やること」を自動調整し、合格までの学習運転を担う適応型学習アプリ**として育てる。

最も強く残す価値は次の一連の接続である。

**教材 → 科目A演習 → 復習 → 弱点補強 → 科目B → 模試 → 学習計画 → 直前期調整**

現在の実装では、試験日、1日の学習時間、直近の学習ペース、問題ごとの正誤・所要時間、忘却状態、誤答理由、教材進捗、科目B進捗、模試履歴などを使い、日々の学習配分・復習・弱点補強・直前期の負荷を変えている。この適応学習ロジックは FE QUEST 最大の差別化要因なので、今後のリファクタリングでも**挙動を壊さないことを最優先**とする。

商品としての中心メッセージは次の方向を維持する。

> **計画どおりに勉強するのではなく、勉強した結果に合わせて計画が変わる。**
>
> あなたが勉強する。FE QUEST が、次の一手を考える。

## 2. v337 時点の評価と判断

第三者AI（Claude）に、v337 の完成版 `index.html` 約3.67MB / JavaScript 約19,771行を実際に解析してもらった。総合評価は **76/100**。重要な評価は以下。

### 高く評価された点

- 自動調整は見せかけではなく、複数シグナルを統合した実用水準の適応型学習。
- 試験までの日数に応じた複数フェーズ、直近実績ペース、忘却曲線、弱点、誤答理由、科目B進捗、模試履歴が実際に学習計画へ接続されている。
- 710問、130テーマ、科目B演習などのコンテンツ量が実装と一致している。
- localStorage中心のPWAとしては、チェックサム、atomic保存、last-known-good、migration journal、IndexedDB復旧点、複数タブ競合防止などデータ保護がかなり強い。

### 主な課題

- `override` の積み重ねと関数の多重ラップが増え、技術的負債が顕在化している。
- 本番runtimeに旧来の hard `assert()` が残り、将来のコンテンツ変更で起動障害につながる理論上のリスクがある。
- 完成版が単一 `index.html` 約3.67MB まで巨大化している。
- 初回ユーザーが試験日・学習時間を設定しないと、最大の差別化である自動調整価値が伝わりにくい。
- 誤答理由は自己申告依存が強く、実測データとのクロスチェック余地がある。
- 商用化にはアカウント・クラウド同期・課金基盤が不足している。

### この評価を踏まえた開発判断

**クラウド同期をすぐに追加しない。**

理由: 現在の localStorage / IndexedDB / migration / recovery / multi-tab conflict に、さらにクラウド同期と同期競合を重ねると、技術的負債が最も大きい状態で最も複雑な状態管理を追加することになるため。

したがって、今後は次の順序で進める。

1. 内部構造を把握する
2. 挙動を変えずに安全性を上げる
3. 初回・日常UXを仕上げる
4. 配信構造を分割する
5. その後にクラウド同期へ進む

## 3. 開発の基本ルール

今後の全バージョンで以下を守る。

### 3.1 学習効果を壊さない

リファクタリング時も、以下の主要挙動を回帰テストで保護する。

- 710問の問題バンク内容とID整合性
- 130テーマの教材構造
- `buildTodayTasks()` 系の今日の学習生成
- 通常期と直前7日の分岐
- 復習期限・忘却状態
- 科目A / 科目Bの配分
- 模試結果から readiness への反映
- 学習履歴・XP・ストリーク・各種進捗保存
- 復旧センター、last-known-good、migration、複数タブ競合
- PWA更新・オフライン起動

### 3.2 大規模一括書き換えをしない

「きれいにするために全部作り直す」は禁止。既存挙動を固定したテストを先に用意し、責務単位で段階的に置き換える。

### 3.3 UX改善は止めない

内部整理期間でも、日常利用で見つかった明確なUI不具合は修正する。ただし、小さな不具合のたびに新しい永久overrideを増やすのではなく、可能なら整理対象の本体側へ吸収する。

### 3.4 新機能より既存価値の完成度を優先

v338〜v342の間は、睡眠・体調入力、バッジ大量追加、SNS機能など大きな新機能は原則追加しない。

### 3.5 「合格確率」と誤認させない

現在の readiness は FE QUEST 独自の「受験準備の仕上がり」指標であり、合格確率ではない。将来60%基準などを表示しても、公開模試・演習上の目安として扱い、実試験の合格予測と断定しない。

   - 問題本文・正答・学習意図を勝手に変更しない

- `時間不足` は、単発申告なら実測回答時間と弱い正答率が一致した場合だけ速度練習へ進める。実測が速い場合は自己申告だけで速度練習へ固定しない。
- 「遅いが正解できている」学習者を回答時間だけで速度不足と判定しない。
- 理由の根拠が弱くても反復誤答が続く場合は、反復復習を優先する。
- `recommendedPrescription()` を追加wrapperで包まず、v343 release生成時に単一の名前付き実装として置換し、技術的負債を増やさない構造にした。
- v343 release validation: 710問、正答位置 178/178/177/177、認知レベル 166/323/221、current contract 71/71、Browser UI contract 23、Subject B semantics、runtime failures 0、fresh first-run、Safari日付入力補正、クラウドruntime継承をPASS。
- profile schemaはv5のまま。productionをv343へ更新済み。

週次トレンド候補は追加監査を実施した結果、通常runtimeがquiz session 20件・各session log 10件・mock history 10件へ履歴を制限しており、活発な学習者では「直近7日 vs その前7日」の前半windowが欠け得ると判明した。`qStats` の集計値から欠損した日別履歴は復元できないため、**不完全な週次データを今日の学習重みに使う変更はv343では見送った。** これによりv343はevidence-confidence guardを完成形として終了し、v344へ進む。詳細: `audits/V343_WEEKLY_TREND_AUDIT.md`。

## 9. 別チャットでの再開手順

ユーザーが別チャットで「FE QUESTの続きを開発したい」「GitHubの最新版から続けて」と言った場合、担当AIは次の順で確認する。

1. GitHub `taiwanwan64/fe-quest` の `main` を確認
2. `FE_QUEST_DEVELOPMENT_PLAN.md` を読む
3. `index.html` / `manifest.webmanifest` / `sw.js` から現行アプリバージョンを確認
4. 直近のmerged PRを確認し、本ファイル記載の「現行アプリ」が古ければGitHub実体を優先
5. 本ファイルの「次の計画バージョン」と、実際に完了済みのPRを突き合わせる
6. 完了済み項目にチェックを付ける / 文書を更新してから次の開発に進む

### 重要

- 古い会話メモに v107 / v111 / v332 等が残っていても、GitHub `main` とこのファイルを優先する。
- 各主要バージョンを完了したら、**同じ開発セッション内でこのファイルも更新する。**
- 少なくとも「現行アプリ」「次の計画バージョン」「完了した項目」「新たに判明した重大課題」を更新する。
- ロードマップ変更が必要な場合は、理由をこのファイルに残す。
