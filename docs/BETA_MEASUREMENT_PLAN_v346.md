# FE QUEST v346 — 小規模外部βの評価方針

対象: 最初の **10〜30人**  
目的: 「FE QUESTが学習者の次の一手を決める価値」を、必要最小限の情報で確認する。

## 1. この段階では自動トラッキングを追加しない

最初の外部βでは、第三者の行動分析SDK、広告SDK、閲覧ページの自動送信、学習履歴の一括収集を追加しない。

理由:

- 現在のFE QUESTはローカルファーストであり、この性質自体がデータ保護上の強みである。
- 10〜30人規模では、プロダクト分析基盤を追加するより、明示的な少数ヒアリングの方が目的に対して十分である。
- 自動計測を追加する場合は、収集項目・保存先・保持期間・同意/通知・プライバシーポリシーの更新を先に確定する必要がある。

## 2. βで確認する主要指標

### 継続

招待したテスターについて、運営側のβ管理記録で次の時点に「FE QUESTを使ったか」を **はい / いいえ / 未確認** の3値だけで記録する。

- 1日目
- 3日目
- 7日目
- 30日目

アプリから学習履歴を自動送信して判定しない。

### 中心価値

テスターへの確認では、次の2点を最優先にする。

1. 「今日の学習」から実際に学習を始めたか。
2. 「次に何を勉強するかを自分で考える負担が減ったか」。

回答は、必要に応じて **はい / どちらともいえない / いいえ** と短い自由記述で集める。

### 補助指標

- 初回設定（受験予定日・学習時間）で迷わなかったか。
- 最近の学習レポート / 試験までのペース表示が理解できたか。
- 科目Bへの導線で迷わなかったか。
- 保存・復旧・クラウド同期で不安や事故がなかったか。

## 3. β管理記録に入れないもの

外部βの管理記録には、次を原則として収集しない。

- 問題ごとの正誤履歴
- JSONエクスポート全文
- localStorage / IndexedDBの内容
- 認証トークンやMagic Link
- Supabaseセッション情報
- パスワード（FE QUESTはMagic Link方式だが、いずれにしても収集しない）
- 不具合再現に不要な個人情報

不具合調査で追加情報が必要な場合も、公開GitHub Issueに機微情報を貼らせない。

## 4. 不具合・改善フィードバック

公開GitHub Issueでは `.github/ISSUE_TEMPLATE/beta-feedback.md` を使用する。

収集するのは、画面/操作、実際の挙動、期待した挙動、再現手順、広い端末/ブラウザ情報、学習データへの影響有無を中心とする。

公開Issueにメールアドレス、認証情報、JSONエクスポート全文などを投稿しないようテンプレート内で明示する。

## 5. 自動分析を追加する条件

次のいずれかが起きるまでは、自動プロダクト分析を追加しない。

- β人数が増え、手動確認では主要指標を追えなくなった。
- 重要な仮説が手動ヒアリングでは検証できない。
- 収集するイベントと保存期間を最小化した明確な設計ができた。

追加する場合は、実装より先に以下を確定する。

1. 送信イベント名と項目
2. 個人を直接識別する情報を含むか
3. 保存先
4. 保持期間
5. 削除方法
6. 利用者への通知/同意方法
7. `privacy.html` の更新

## 6. β開始の判断

外部招待を開始する前に、少なくとも次を満たす。

- productionが既知の安定版である。
- `privacy.html` が現行productionの実装と一致する。
- βフィードバックテンプレートが利用できる。
- クラウド同期が任意・ローカルファーストである。
- アカウント削除とクラウドデータ削除の導線が生きている。
- 回帰テストが通っている。

この文書は「βを自動で開始する許可」ではない。実際の招待人数・招待先・開始日は別途、人が判断する。
